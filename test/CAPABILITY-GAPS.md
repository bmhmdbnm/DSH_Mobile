# 测试能力缺陷记录

记录"想测但测不了 / 测不准"的地方，避免每次重新踩。**已解决**的留着，因为下次改这块
代码会用到它的原因和解法。

分类：`交互` 操作做不到或不可靠；`判据` 观察不到或者不准；`环境` 跑不起来或跑不稳。

## 交互-1 滑动被容器吃掉，页面纹丝不动 ✅ 已解决

- **症状**：`swipe` 报成功，但前后两张截图逐像素相同；断言随后报"屏幕上没有 xxx"，
  看起来像 App 缺陷。
- **原因**：三个叠加。① 拖拽锚在窗口中间、位移只有 0.4 屏，落在 List 之外或太短；
  ② 长按式拖拽（`press(0.05...)`）被 SwiftUI 的 List 当成按压而非滚动；
  ③ 判断"动了没动"用的是截图字节比较，一次重绘就能让它误判成功，于是不再重试。
- **解法**（`Engine.swift` 的 `swipe`）：
  1. 目标依次取：用例指定元素 → 最大可滚动容器 → 已知页面容器（`settings.root` 等）；
  2. 三种策略依次尝试，每种最多 3 次：元素自身 `swipeUp()` → 坐标拖拽（位移 0.85 容器高）
     → `XCUIElement.scroll(byDeltaX:deltaY:)`；
  3. 是否成功改为**按文字元素整体位移判定**：至少 3 项文字移动 >6pt、且 70% 同向，
     才算真的滚动了；日志里报告位移项数与中位位移（例：`13 项文字位移，中位 -480pt`）。
- **注意**：设置页的 `List` 在无障碍树里不是 `scrollView` 也不是 `table`，而是
  `CollectionView`，且 `hittable=false`。

## 交互-2 刚弹出的页面第一次滑动常被吞 ⏳ 部分解决

- **症状**：刚 `launch` 完就滑，第一次常常无效。
- **原因**：sheet 的入场动画与列表首帧布局尚未结束，手势落在过渡态上。
- **现状**：每种策略重试 3 次，实测已能成功；但代价是可能多花 1–2 秒。
- **彻底解法**（未做）：进入页面后事件驱动地等列表稳定再开始步骤——现在只等
  "连续两帧相同"，对首帧布局不算充分。

## 判据-1 截图时机：动作前还是动作后 🟡 有约定

- **症状**：`shot` 挂在有动作的步骤上时，图拍在动作**之前**，"下滑后"的图其实是下滑前。
- **现状**：用 `shot ... after` 明确要求动作后再拍；引擎会先等到画面稳定
  （`waitUntilStill`）再让外部截图，避免拍到动画中间帧。
- **风险**：忘了写 `after` 就会得到一张误导的图，而报告里看不出来。

## 环境-1 测试进程看不到 Mac 的文件路径 ✅ 已解决

- **症状**：计划文件传 `/Users/...` 路径，测试里读不到，`DSH_PLAN is unset`。
- **原因**：UI 测试进程跑在仿真器里，宿主机路径对它不可见。
- **解法**：计划与事件流写在**运行器自己的容器**里（`simctl get_app_container`），
  引擎用容器内相对路径读；容器在重装后会变，每轮重新解析。

## 环境-2 XCUITest 驱动的 App 不在仿真器可见屏幕上 ✅ 已解决

- **症状**：整轮所有 `simctl io screenshot` 都是桌面壁纸，而断言全部通过。
- **原因**：XCUITest 管理的 App 不渲染到仿真器显示通道。
- **解法**：截图由**引擎自己拍**（`XCUIScreen.main.screenshot()`），以附件导出再用
  `xcresulttool` 取回；`shot` 动作拍的是仿真器屏幕本身，用于取证桌面/系统界面。

## 环境-3 XCTest 失败后重复整个测试方法 ❌ 无法关闭

- **原因**：失败重跑是默认行为，`-retry-tests-on-failure NO` 不接受值，
  `-test-iterations 1` 非法，测试计划文件在当前 Xcode 版本下读不进去。
- **现状**：运行器对同一步只保留最后一次判定与截图；副作用是失败一轮耗时约 3 倍。

## 环境-4 附件名被 XCTest 改写 ✅ 已解决

- **症状**：`shot|s01|sessions` 变成 `shot_0_UUID.sessions`，导出时认不出自己的证据。
- **解法**：证据标签改用 `~` 分隔，并用**步骤序号**而不是步骤 id 作为配对键
  （同一个用例里两处都可能把截图叫 `settings`，按名字配对会互相覆盖）。

## 环境-5 同一分钟内两次运行会共用目录 ✅ 已解决

- **症状**：截图目录里混进上一次运行的同名图片，报告引用了旧图。
- **解法**：运行号精确到秒；每轮开始前清空 `shots/`、`annotated/`、`detail/`。

## 判据-6 中文在 Web 视图里渲染成方框 ✅ 已解决

- **症状**：报告在 App 的 HTML 预览里整页中文是方框，英文数字正常。
- **排查**：设备端诊断屏（`-DSHOpenScreen diagnostics`）回答了两个事实：
  系统字体 `.AppleSystemUIFont` 的字符集**画不出「报」**；而 `PingFang SC` 作为字体族
  存在、可以按名字取到。WebKit 只按样式表里点名的族去找字形，不享受原生视图那套
  内部回退，所以 `-apple-system` 在 iOS 上等于"没有中文"。
- **解法**：报告 CSS 显式点名中文族：
  `"PingFang SC", "Hiragino Sans GB", "Heiti SC", "Helvetica Neue", sans-serif`。
  macOS 上浏览器本来就用 PingFang 显示中文，所以两端结果一致。
  代价：拉丁字符改用 PingFang 的拉丁字形，不再跟随系统 UI 字体。
- **试过但无效**：`@font-face` + `local()` + `unicode-range`（WKWebView 不解析
  `local()`）；给 Info.plist 加 `CFBundleLocalizations: zh-Hans`（与本地化无关）。

## 判据-7 超长单行会把文本阅读器卡死 ✅ 已解决

- **症状**：手机上打开第一版测试报告（6 张图 base64 内嵌、单行 31 万字符），
  一直转圈然后 App 被杀。
- **原因**：阅读器把每一行当成一个 `Text` 排版，31 万字符的一行排不动。
- **解法**：`CodeHighlighter.page` 对超过 2000 字符的行只显示前 2000 并注明
  「… 本行还有 N 个字符未显示」。文件本身不动，报告改用 `media/` 引用后也不再产生长行。
- **回归用例**：`TC-MOB-02`（20 万字符单行的 fixture）。

## 环境-7 Release 配置下的编译错误只在发布时才暴露 ✅ 已解决

- **症状**：Debug 与仿真器一切正常，`deploy-ota.sh` 归档失败。
- **原因**：新增的自动化钩子 `automationFile()` 与诊断屏漏了 `#if DEBUG` 的 Release
  分支，而调用点不在条件编译里。
- **解法**：补上 Release 空实现；新增 `./test/run.sh release`（Release / 真机归档），
  **发布前必跑**——仿真器全绿不代表能发。

## 判据-8 词法高亮对中文数字死循环 ✅ 已解决

- **症状**：手机上把 HTML 报告切到「源码」后一直转圈，主线程被占满（看起来像卡死/崩溃）。
- **根因**：`CodeHighlighter` 用 `Character.isNumber` 判断数字字面量，而 `两`、`三`、`十`、
  `万` 这些汉字的 `isNumber` **为真**；于是进入数字分支，但内层用的 `isNumberBody` 又不认
  它们，索引不前进 → 死循环。含「两个入口」这类措辞的文本必然触发。
- **定位方式**：把词法单独编译到 macOS 上逐行跑（`swiftc lexer.swift main.swift`），
  二分到出问题的那一行与前缀，再在循环里加计数守卫打印自旋位置。
- **解法**：进数字分支要求 `isNumberBody(character)` 为真；标识符分支也加了「不前进就按
  普通字符前进一个」的兜底，保证任何输入下循环都会推进。
- **回归用例**：`TC-MOB-03`（源码方式打开含中文数字的报告）。
- **教训**：字符分类判断必须与"该分支的消费条件"一致，否则任何语言的输入都可能把词法
  卡住；写词法时循环体必须有推进守卫。

## 交互-7 无目标的坐标手势会误伤数据 ⛔ 已加防护（事故记录）

- **事故**：调试行级左划时，目标行已从树上消失，引擎仍按窗口坐标执行了一次横向拖拽，
  把当时停在手指下的**一个真实会话**归档了——而这个版本的 DSH 没有取消归档的接口。
- **根因**：`press(forDuration:thenDragTo:)` 既会在目标缺失时退化成"拖过整个窗口"，
  也会在部分元素上抛 `Pointer events are not supported for this device`（进程级异常，
  `continueAfterFailure` 拦不住，整轮直接结束）。
- **防护**：引擎里已删除全部坐标拖拽与坐标点击兜底；滑动/点击只走元素自身手势，
  元素不可点就如实判失败；列表行滑动前必须确认目标存在且完整可见。
- **教训**：破坏性手势（左划、长按菜单）在任何情况下都不允许"没有目标就照坐标来"。
  测试可以失败，数据不能。

## 交互-4 归档是单向的 ✅ 已按事实处理

- **事实**：host 的 `workspace/archiveSession` 接受 `archived:false` 但**忽略**它，也没有
  unarchive 方法（实测：归档后集合大小不变）。所以「撤销归档」在协议层不存在。
- **处理**：界面不做撤销按钮，改为提示「可在电脑端找回」；归档只把会话移出工作区分组
  界面，不删除任何文件。
- **找回**：手机上「已归档」折叠区列出全部归档会话，可以打开查看/继续。真要移出归档集合，
  只能改 host 存储后重启 DSH：`python3 scripts/dev/restore-archived.py --list` /
  `--remove <sessionId>`（见脚本内说明，顺序必须是先退 DSH 再改再启）。
- **教训**：先验证接口是否真的具备可逆性，再决定界面上给不给「撤销」。

## 交互-5 无障碍标识会往下传 ✅ 已解决

- **症状**：「撤销」按钮按自己的 id 找不到。
- **原因**：SwiftUI 把容器上的 `accessibilityIdentifier` 推给子元素，覆盖了子元素自己的
  id——元素树里两个东西都叫 `session.archive.banner`。
- **解法**：标识放在各自元素上，不要放在容器上。

## 交互-6 元素代理会失效，手势失败会中止整轮 ✅ 已解决

- **症状**：行级左划偶发 `No matches found for ... IN identifiers`，XCTest 记为失败并
  因为 `continueAfterFailure = false` 直接结束这一轮。
- **原因**：SwiftUI 重建列表行后，之前取到的 `XCUIElement` 代理失效；而 `swipeLeft()`
  这类手势在代理失效时会抛 XCTest 失败。
- **解法**：手势前重新解析元素；行级滑动不走「元素自身手势」，改用坐标拖拽；滚动手势
  只在目标是可滚动容器时使用。

## 测试-1 造数据必须用临时会话 ✅ 已解决（能力已固化）

- **要求**：规则里写着「不许碰真实数据」，但归档/新建这类功能天然要动会话。
- **解法**：用例 front matter 写 `临时目录: /tmp/xxx`，运行器就先在那个目录建一个会话
  作为用例的操作对象，并把 `.steps` 里的 `{{session}}` 换成它；跑完按 host 报告的 cwd
  删掉该目录下的所有会话（含用例通过界面新建的那些）。
- **注意**：会话目录里没有 meta.json，cwd 只能问 host——早期按文件找 cwd 的清理等于
  什么都没删，留下一堆空会话（已清理）。

## 业务-1 部分界面只在特定连接方式下出现 ✅ 已解决

- **症状**：设置页的「已配对的设备」在直连（`dsh://direct`）下根本不渲染。
- **原因**：该分组要求中转的管理能力；直连没有，代码如实地隐藏它
  （`SettingsModel.devicesAvailable`）。
- **影响**：此前所有用例都走直连（`host.mjs` 只发 `dsh://direct`），这一屏始终测不到；
  TC-UI-01 的 s11 因此在 20260916-230050 失败，而在更早「App 恰好连在中转上」的几轮通过——
  同一份代码两种结论，看起来像随机失败。
- **解法**（已做）：`run.mjs` 认 `DSH_CONNECT=relay`：跑之前由**运行器**配对
  （`test/tools/relaypair.mjs` 领码 → 认领 → 把 `dsh://relay?…` 凭据交给 App），
  跑完在 `finally` 里撤销。

  ```bash
  DSH_CONNECT=relay ./test/run.sh run test/cases/fixed/01-全部独立页面逐屏核对.md
  ```

- **为什么由运行器领码**：配对码一次性，只有认领方拿得到 `deviceId`；让 App 领，跑完就没
  人能撤销那一行——用户设备列表里每跑一轮多一行 `DSH-Test`。撤销失败会红字提示，
  让人到手机上手删（那说明中转或网络出了问题）。

## 判据-13 像素核对读的是错位像素 ✅ 已解决

- **症状**：无——核对一直「通过」，所以没人发现它在读错的像素。
- **原因**：`verify.mjs` 的 `loadImage()` 里 `bytes = depth / 4`。`sips` 写的是 **24 位**
  BMP，每像素 3 字节；按 4 算出来是 6，于是横向每两个像素取一个，越过行中段后还读到
  下一行的像素。
- **影响**：所有 `check=texts,amber` 的结论都建立在错位取样上；容差又是照着这些数字
  调的，所以看起来一直合理。
- **解法**（已做）：改成 `depth / 8`（32 位 BMP 得 4，24 位得 3）。
- **同类漏检**：黄色判定上限原为 hue 55°，而**纯黄正好是 60°**——深色模式把边框渲染成
  `#FFFF0F` 时该判定报 0.000%，「改了颜色但手机上仍是旧配色」正是这么漏过去的。
  上限已扩到 70°。

## 环境-6 `after` 截图曾经没有图片 ✅ 已解决

- **症状**：用例里写了 `shot x after`，判定有、图没有。
- **原因**：`after` 只发了事件给运行器，没有让引擎自己拍附件；而截图证据只从
  xcresult 的附件里导出。
- **解法**：引擎在动作之后自己拍（`takeScreenshots(named:for:)`），运行器只负责归档。
- **注意**：这也是「iPhone 上没有图片」的排查弯路——先查渲染，其实是导出侧缺文件。

## 判据-10 用例用语里 `timeout` 与只拍照行的两个坑 ✅ 已解决

- **症状一**：`等待 text:x timeout=120` 报「缺少目标」——整行被当成一个选择器。
  **原因**：`等待` 的动词规则没有把 timeout 单独分组，随后被 `quote()` 连成一个词。
- **症状二**：`等待消失 id:x timeout=120` 悄悄退回默认 20 秒，等真实一轮回答时会误判失败。
  **原因**：`wait_gone` 分支没把 `timeout` 抄进步骤。
- **症状三**：`do: 什么都不做 | want: … | shot: …` 声明了截图却一张都没有。
  **原因**：没有动作的行只有断言步骤，而截图只挂到"动作步骤"或"纯拍照行"上。
- **解法**（`case.mjs`）：三条都补齐——timeout 进独立分组并转发、截图挂到首个断言步骤。


## 判据-11 首屏断言会随数据变化而失效 ⏳ 有绕法（本轮实战踩到）

- **症状**：`TC-UI-01` 步骤 8 断言 `text:权限` 在首屏。20260916-150455 那次通过，
  代码不变的 20260916-181949 那次失败——两次之间「已配对的设备」从 3 行涨到 5 行，
  把「权限」分组挤出了首屏（`git log 3a81353..24e29c1 -- Features/Settings` 无提交）。
- **原因**：`assert` 看不到滚动之外的内容（同判据-2），而**首屏有多少东西取决于可变数据**
  （设备列表、会话数、更新横幅）。这类断言写的其实不是"有没有"，而是"当下这一屏有没有"。
- **绕法**：需要断言的元素若可能在屏外，先 `滚动到 <目标>` 再断言；或在用例里只断言
  首屏必然存在的分组，屏幕外的部分交给截图与人工核对。
- **教训**：写"首屏有 X"这类断言前，先问 X 会不会被别的数据挤下去；会，就不是断言对象。

## 判据-12 设置页变长后「滚动到 <文字>」稳定失败 ⏳ 未解决

- **症状**：`TC-UI-01` 步骤 9 的 `滚动到 text:关于` 连跑两次都是
  「滚了 12 屏也没找到 text:关于」；步骤 8 试过 `滚动到 text:权限` 同样失败。
  而 20260916-150455 那次同为 `滚动到 text:关于`，一次就过。
- **变化**：两次之间设置页的「已配对的设备」从 3 行涨到 6 行（relay 上累积的
  测试设备没清），权限、凭据、提醒、关于都被推到列表更深处。
- **原因（推测）**：`scroll_to` 每轮先查一次元素树再 `swipeUp()`，共 12 轮；
  设备列表是网络数据，弹出时还在到达，SwiftUI 重建 List 会把滚动位置带回去，
  于是 12 屏都在原地打转。也可能是 12 屏不够——两种情况现有日志分不出来。
- **绕法**：需要断言的分组若在列表深处，先确认它是否一定在首屏；不确定就不要下断言，
  留给截图人工核对（当前 TC-UI-01 就是这么处理的）。
- **彻底解法（未做，二选一）**：
  ① 产品侧：设置页的设备列表限高或折叠（列表长度不随数据无限增长，滚动才有确定行为）；
  ② harness 侧：`scroll_to` 改成「等到内容稳定再滚」（连续两次元素树快照一致才开始），
     并区分「列表还在变」与「确实滚不到」两种失败。

## 环境-8 L2 容器：镜像源与 DNS 会被 colima 重置 ⏳ 有脚本

- **症状**：容器拉不动镜像。两种失败叠在一起：`failed to resolve reference ... dial tcp: lookup
  registry-1.docker.io on [::1]:53: connection refused`（DNS），以及直连 `registry-1.docker.io`
  本就超时。
- **原因**：① colima **每次启动都会重写** VM 里的 `/etc/docker/daemon.json`，而 colima 0.10.3
  的配置里没有 `registry-mirrors` 这个键——手工写进去的镜像源会被清掉；② 镜像里的
  `/etc/resolv.conf` 是**悬空**符号链接（systemd-resolved 没跑），dockerd 于是去问 `[::1]:53`；
  而且 Go 的解析器会把 resolv.conf 缓存住，所以补写之后**必须重启 dockerd**。
- **解法**：`sh scripts/verify/l2-vm-setup.sh`（幂等：补镜像源、重写 resolv.conf、重启 docker）。
  跑完 `docker info --format '{{json .RegistryConfig.Mirrors}}'` 应看到镜像源。
- **注意**：`lane:l2` 的 doctor 以 dockerd 自报（`docker info`）为准，不看 colima 的配置文件——
  按文件判断会得到假结论。

## 判据-13 共享挂载不转发 inotify，会让"文件监听"类结论假阴性 ⏳ 已知，用机制规避

- **症状**：在容器里 `fs.watch` 一个**共享挂载**（virtiofs/9p/sshfs）的目录，宿主侧改文件时
  容器里一个事件都收不到——看起来像"宿主没有热更"，其实是观测手段失效。
- **证据**：`npm run lane:l2 -- run --scenario selfcheck` 里的**反向对照**：同一个 watcher 放在
  容器卷上能看到 `rename,change`，放在共享挂载上由宿主写入则是 `(none)`。
- **解法**：L2 的硬约束是**代码复制进卷**（`docker cp` / `COPY`），不靠共享挂载；`selfcheck`
  把这条对照固化成渠道自检，前提不成立就判 `blocked`，不给结论。
