# test/ —— 仿真器用例测试

> 面向：实现者 · 状态：stable · 最近核对：2026-09-20

用例是结构化中文，测试者（AI）按用例在仿真器里执行、看截图、给判定。
规则见 `RULES.md`，**报告必须长什么样见 `REPORT-CONTRACT.md`**，页面清单见 `screens.md`。
通用测试标准（用例怎么写、证据要到什么程度、四态怎么判）在全局 skill
`agent-testing` 里；这台机器上怎么驱动仿真器在 `ios-sim-testing` 里。

## 五个动作

用例文件名是「序号-中文标题」，例如 `01-全部独立页面逐屏核对.md`；
用例文件里的 `id`（如 `TC-UI-01`）是不变的引用名，报告与提交信息用它。

```bash
./test/run.sh prepare                 # 查端点、起仿真器、必要时编译（增量）
./test/run.sh plan [用例.md]          # 看用例被翻译成什么（不执行）
./test/run.sh release                 # 用发布配置编译（发布前必跑）
./test/run.sh run [用例.md]           # 执行一条用例（默认 01）
./test/run.sh shot <名字> [--note x]  # 立刻截一张当前画面
./test/run.sh scaffold                # 生成本次运行的 review.md 骨架（逐步占位）
./test/run.sh report --verdict 通过 --note "一句话结论" --basis "判定依据"
./test/run.sh ls                      # 已有运行
```

测哪些用例、什么时候补一张图、看图后判通过还是失败，都由测试者决定。
这五个动作只做机器那部分：驱动、截图、像素核对、lint、排版。一轮典型用例约 40 秒
（增量编译 2 秒 + 启动一次 xcodebuild + 逐屏执行）。

**`report` 是闸门**：`--verdict` 必填（没有「待审视」默认值）；`review.md` 缺声明、
缺步骤、`实际` 复述期望、证据不可核对，报告会判为 **报告不完整** 并在顶部列出每一项，
补齐 `review.md` 后重跑 `report` 即可，不需要重跑用例。

**连接通道**：默认用 DEBUG 直连（`-DSHConnectURL dsh://direct…`），够快，但产品只提供
中转——只在直连下存在的差异测不出来，而只在中转下出现的界面（设置页的「已配对的设备」）
根本不会渲染。要按产品通道跑：

```bash
DSH_CONNECT=relay ./test/run.sh run test/cases/fixed/01-全部独立页面逐屏核对.md
```

运行器自己配对、跑完自己撤销（`test/tools/relaypair.mjs`）：配对码是一次性的，谁领谁才知道
device id，所以让 App 去领就等于没人能撤销——以前每跑一轮，用户设备列表里就多一行
`DSH-Test`。现在用的是「先领码 → 把凭据交给 App → `finally` 里撤销」，撤销失败会红字提醒
到手机上手删。

lint 自己也有测试——改了 `report.py` 的规则就跑一遍：

```bash
test/.venv/bin/python test/tools/test_report.py    # 每条规则一个反例，全部通过才算可用
```

## 目录

| 路径 | 内容 | 进 git |
|---|---|---|
| `RULES.md` | 判定规则，用户维护 | ✅ |
| `REPORT-CONTRACT.md` | **报告契约**：章节、`review.md` 写法、lint 规则 | ✅ |
| `CAPABILITY-GAPS.md` | 测试能力缺陷记录（做不到 / 测不准的地方） | ✅ |
| `screens.md` | 可直达页面与根标识 | ✅ |
| `cases/fixed/` | 固定用例，只增不改；每个用例两个文件：`序号-中文标题.md` + 同名 `.steps` | ✅ |
| `fixtures/` | 用例要用到的固定输入（如报告 fixture 与它的预览图） | ✅ |

`fixtures/` 里的报告是某次真实运行的副本（`report.html` 改名 + `media/` 一起拷），
复制方法：把 `test/runs/<运行>/report.html` 与 `media/` 拷进 `test/fixtures/`，
HTML 里的 `src='media/…'` 保持不动即可。这样做是为了让用例不绑死在某次运行的目录上。
| `cases/current/` | 本次任务的临时用例 | ✅（随任务结束清理） |
| `tools/` | 执行器（见下） | ✅ |
| `runs/<年月日-时分>/` | 每次运行 | ❌ |
| `runs/<运行>/report.html` | **给人看的报告**（截图已内嵌，单文件可读） | ❌ |
| `runs/<运行>/shots/` | 原图 | ❌ |
| `runs/<运行>/annotated/` | 带判定与说明的标注图 | ❌ |
| `runs/<运行>/review.md` | **步骤评审**：声明、每步的实际现象/依据/结论、发现、回归 | ❌ |
| `runs/<运行>/detail/` | 中间产物：xcresult、事件流、用例翻译、像素明细 | ❌ |
| `.venv/`、`.build/` | 标注环境与中间文件 | ❌ |

> **`fixtures/media/` 与 `docs/artifacts/screenshots/` 不入库。** 那些图都是从真机会话截的，
> 含家目录、设备名与项目名，已从仓库移除并写进 `.gitignore`，只在作者本机保留。
> 新克隆的仓库里 fixture 报告仍可打开、文字判定照常通过，只是图片位置显示为缺图；
> 要补齐就按上面的方法拷一份自己的 `media/` 进去。

## 怎么跑起来的

1. `tools/context.mjs` 读本机 DSH 端点（`$DSH_HOME/mobile-link/endpoint.json`，由连接器写出；
   自研外壳那条 `dsh-shell.log` 退路已随外壳删除），
   并在跑的时候采一份环境事实（仿真器名、设备型号、iOS 版本、Xcode、测试机）。
2. `tools/case.mjs` 把用例翻译成计划 JSON（含 front matter 的 `通过判据`）。
3. 计划经**仿真器容器**交给 XCUITest 引擎（测试进程看不到 Mac 的文件路径）。
4. 引擎逐步执行、逐步截图（附件形式），把每步判定写进事件流。
5. `tools/run.mjs` 从 `.xcresult` 导出截图，按用例要的名字归档，并把
   `summary.json` 写全：判定、计数、环境、耗时、判据、同用例历史运行。
6. `tools/verify.mjs` 做像素核对；`tools/annotate.py` 把判定画到图上。
7. 测试者看过截图后写 `review.md`（声明、逐步的实际现象与依据、发现、回归），
   这是报告里「实际现象／判定依据／本步结论／发现」的来源；`scaffold` 先把骨架填好。
8. `tools/report.py` 先按 `REPORT-CONTRACT.md` 做 lint，再写成 `report.html`：
   报告头、判定（四态＋依据＋**结论建议**合入/有条件合入/不合入＋**指标概览**）、
   **通过判据**、执行前声明＋**测试环境**、发现、逐屏核对（操作/期望/实际/依据/结论，附该步截图）、
   未覆盖与风险、上轮问题回归、产物。
   截图引用 `media/` 里的缩略图（640px 宽 JPEG），所以从浏览器、文件查看器、
   或单独转发出去都能看到图；全分辨率原图仍在 `shots/` 与 `annotated/`。
   lint 不过时报告顶部列出每一项，判定写「报告不完整」。

## 步骤评审怎么写

先 `./test/run.sh scaffold` 生成骨架（每一步的 id、操作、期望都填好了），再补三项：
**声明**（跑之前写）、每步的 **实际现象 + 判定依据 + 结论**、有缺陷时写 **发现**。
字段与 lint 规则见 `REPORT-CONTRACT.md`，一句话要求：

- `实际` 写观察到的事实——条数、位置、耗时、报错原文——**不许复述期望**；
- `依据` 写凭什么这么判（截图编号、事件流 id、像素核对结论）；
- `结论` 取四态；连续多步可以写成 `## r1–r16`，但每步都要有结论。

```markdown
## 声明

构建: 3a81353 Debug，仿真器 <UDID>，App 1.0
数据: 只读打开真实会话；无写入、无造数据
边界: 只核对首屏可见内容；屏幕外只留截图不做断言
基线: 上轮无遗留未解决问题

## r4

操作: 打开一个真实会话的转写
实际: 47 行消息渲染完整，最后一行是「已完成」分隔线，无截断
依据: 截图 02 与 detail 事件流 s05 一致；像素核对无错误色
结论: 通过
异常: 无
```

引擎只知道元素有没有回应查询，说不了「渲染正常」这类话——所以每步的「实际现象」
与「本步结论」由测试者写完放这里，报告照它渲染。改这个文件再跑 `report` 即可，不用重跑用例。

## 用例怎么写

**两个文件，各管一件事。**

`01-全部独立页面逐屏核对.md` —— 纯自然语言，给人和评审看，不含任何机器指令；
front matter 里必须有 `通过判据:`（这条用例「什么算通过」先写死，报告第 2 节原样列出）：

```markdown
---
id: TC-UI-01
title: 全部独立页面逐屏核对
用例版本: 4
通过判据: 12 个步骤的结论全为通过；6 张留证截图逐个看过，无截断、无重叠、无错误色；像素核对全部通过；没有未验证或可疑的步骤
---

# TC-UI-01 全部独立页面逐屏核对

## 步骤

1. 连接本机 DSH，进入会话列表，截图留证。
2. 确认列表页的两个工具栏入口都在：连接管理、设置。
```

`01-全部独立页面逐屏核对.steps` —— 逐行对应上面每一步，只写机器要做的：

```
1  do: 连接本机 DSH        | shot: sessions check=texts,amber
2  do: 什么都不做          | want: label:连接管理 | label:设置
```

第 N 行对应第 N 步，数量必须一致（不一致会直接报错）。改测试通常只改 `.md`；
只有换页面、加断言、加截图时才动 `.steps`。想确认翻译结果：`./test/run.sh plan`。

`.steps` 的字段与用语表见文件顶部的注释；一句话概括：

| 字段 | 含义 |
|---|---|
| `do` | 这一步做什么（连接本机 DSH / 不连接 DSH [screen=x] [args=…] / 打开页面 x / 点击 x / 输入 x / 滚动 up / 等待 x / 探查 / 什么都不做）。`不连接 DSH` 的 `args=` 会把启动参数交回用例：App 只读**第一个** `-DSHConnectURL`，要自己给一个 `dsh://pair?…` 之类的链接就必须先让运行器别塞它那条 |
| `want` | 要满足的检查，可写多个，用 `|` 分隔；空着表示只看截图 |
| `shot` | 截图名字，可加 `check=texts,amber`；末尾标 `after` 表示动作之后再拍 |

选择器（写在 `want`/`shot` 的目标里）：`id:` 无障碍标识、`label:` 无障碍标签、
`text:` 屏幕文字；**含空格要用双引号**。

早先的写法（指令直接写在 `.md` 里）已经废弃：用例文件应该只是用例。

指令表：

| 指令 | 作用 |
|---|---|
| `launch connect=auto\|none [screen=…]` | 启动 App；`screen` 取 `screens.md` 的名字，可逗号并列 |
| `tap id:x` / `tap "label:文字"` / `tap "text:文字"` | 点按 |
| `type "text:要输入的字" text=…` | 输入 |
| `swipe direction=up\|down\|left\|right [on=…]` | 滚动；不指定目标时找最大可滚动容器，并校验真的滚了（报位移量） |
| `wait id:x timeout=15` | 等待出现 |
| `assert id:x` / `assert "text:文字"` / `assert id:x contains=…` | 断言存在或包含文字 |
| `shot sessions check=texts,amber [after]` | 要一张截图；`after` = 在动作**之后**拍（拍滑动结果时必须写） |
| `滚动到 <目标>` | 一屏屏滚，直到目标出现（断言看不到屏幕外的东西，所以要先滚到） |
| `等待消失 <目标> timeout=20` | 等某元素消失（弹层关闭、横幅超时） |
| `id~:<前缀>` | 标识以该前缀开头的任意元素（例：`id~:session.row.` 表示任一行会话） |
| `切到后台 5 秒` / `切回前台` | 模拟按 Home 再回来 |
| `打开报告 <文件>（锚点）` / `打开源码 <文件>` | 用 App 的文件查看器打开工作区文件；括号里是判定「到了」的文字 |
| `{{session}}` / `{{pick}}` | 占位符：前者是本次运行的临时会话，后者是运行器挑的真实会话（只用于「界面还在」这类只读断言） |

选择器：`id:` 无障碍标识、`label:` 无障碍标签、`text:` 屏幕上的文字。
**目标里有空格要用双引号包起来**，否则会被当成两个参数。

## 加一个新的可直达页面

1. App 里给这一屏的根元素加 `accessibilityIdentifier`（例如 `files.root`）。
2. `tools/context.mjs` 的 `screens` 表加一行：根标识 + 启动参数。
3. `screens.md` 登记。
4. 在 `TC-UI-01` 里加一行。

## 临时会话（造数据）

需要动会话的用例（归档、新建）在 front matter 写一行：

```
临时目录: /tmp/dsh-uitest-scratch
```

运行器会先在这个目录建一个会话，把它作为 `{{session}}` 交给用例，跑完删除**该目录下的
所有会话**——包括用例通过界面新建的那些。真实历史不会被当成实验对象。

需要「某个特定状态的会话」时，在 front matter 写一行会话 id：

```
会话: session-1a2b3c4d-…
```

运行器默认挑的是**历史最多**的那个会话，那是「大小」不是「状态」——带待答问题的会话
按大小永远挑不出来，而用例要的正是那个状态。写 `会话:` 时以它为准（`{{pick}}` 与
`打开页面 transcript` 都用它）。

## 报告在手机上读

报告是给浏览器看的 HTML，可以放进工作区文件在 iPhone 上打开：
`.html` 默认进「渲染查看」（WKWebView，与 Mac 同一套 CSS），工具条上可切「源码」。
验证用例：`test/cases/current/01-手机上阅读测试报告.md`。

两条已知限制（见 `CAPABILITY-GAPS.md`）：渲染/源码的切换按钮在 Web 视图工具栏里、
自动化点不中；报告正文的滚动在自动化里不稳定。

## 遇到测不了的情况

先查 `CAPABILITY-GAPS.md`：那里记着已知做不到或测不准的地方、原因和绕法。
新发现的能力缺陷按同样格式追加一条（症状 / 原因 / 解法 / 状态）。

## 已踩过的坑

- **XCUITest 驱动的 App 不在仿真器可见屏幕上**，`simctl io screenshot` 拿到的是桌面。
  所以截图由引擎自己拍并以附件导出；`shot` 动作拍的才是仿真器屏幕本身。
- **附件名会被 XCTest 清洗**：`|` 会被换成 `_`，证据标签用 `~` 分隔。
- **测试进程看不到 Mac 路径**：计划与事件流都放在仿真器容器里传递。
- **XCTest 失败后会重复整个测试方法**，且没有开关关掉：报告对同一步只保留最后一次。

## 机器不核对的东西

- **分隔线**：试过按行找横线，在设置页那种 1px 浅灰分隔线上稳定漏检，会把正常界面
  误判成缺陷。改由人看截图（实现留在 `verify.mjs` 的 `countLines`，未启用）。
- **元素重叠**：无障碍树天然嵌套，按 frame 求交会把父子关系全报成重叠。同样看截图。
- **屏幕外的内容**：断言看不到滚动之外的元素，那部分只做截图留证。

## 用例模板

`test/examples/` 里有两份可复制的模板：`01-只读检查`（不碰任何会话）与
`02-临时会话里发一句话`（写入类，声明 `临时目录:` 让运行器新建并回收会话）。

写新用例时复制模板到 `test/cases/current/`，改名后补同名的 `.steps`。**写入类用例必须声明会话
归属**（`临时目录:` 或钉住自己的 `会话:`），否则运行器拒绝执行——这条守卫是因为曾经有用例把测试
提示发进了真实会话。
